# 踩过的坑 —— 完整清单

> 这份文档记录本项目从 0 到"能正常读书"过程中**真实发生过**的每一个坑。
> 每条都写：**现象 → 根因 → 为什么当时没发现 → 修法 → 教训**。
> 写下来的唯一目的：下一个接手的人不要再踩一遍。

---

## A. 章节结构：最容易"看起来没问题"的一类

### A1. 规则包的 `enable=false` 被读了，但没有完全执行

- **现象**：4.33 MB 的网文被识别出 **16,060 个"章节"**（正常应 500~2,000）。抽样能看到
  `========================`、`《这么可爱真是抱歉》`、`下意识的，都开始考虑起《智慧树》录制之后的事情了。`
  这类"标题"。
- **根因**：规则包 `txtTocRule.json` 里 26 条规则有 14 条 `enable=false`（激进规则默认关闭，这是
  成熟阅读器的产品语义）。我们的 `ChapterCandidateScanner` **只对 `regexRisk >= HIGH` 的禁用规则跳过**：
  ```kotlin
  if (rule.regexRisk >= RegexRisk.HIGH && !rule.enabled) continue   // ← 只有高风险才尊重 enable
  ```
  于是禁用中的**低/中风险宽泛规则**（`特殊符号 标题(成对)`=`《…》`、`特定字符 标题 特定符号`=`====`、
  `顶格标题`、`通用规则`）照样扫描、照样进解析序列。
- **为什么没发现**：这些规则"确实匹配到了东西"，解析器也没崩；坏结果只体现在**章节数量**和
  **下游取文范围**上，不体现在任何单测里。
- **修法**：`enable=false` 一律不扫描；激进规则只能由用户在【章节规则】页显式启用。
- **教训**：**规则包里的开关语义必须在扫描器里 100% 兑现**。部分兑现比不兑现更危险 ——
  它让"关闭"看起来已经生效了。

### A2. `revision.chapters` 是**候选集合**，不是章节序列

- **现象**：下游按 `chapters[50]` 当"第 50 章"，拿到的是 REJECTED 的假章节；`contentEndLine`
  对非末章是 `null`，下游默认成"到文件末尾" ⇒ **跨章取文**。
- **根因**：`StructureRevision.chapters` 里混着 `CONFIRMED / PROVISIONAL / REJECTED / TOC_ENTRY`。
  它是**诊断视图**，不是产品数据。
- **连锁放大（这是"慢"的真正来源）**：假章节 → 取文过大 → 段落恢复扫大量文本 → 片段数暴涨
  → 连标构造反复 → Director 任务"看起来特别慢"。**我们花了很久在优化 Director，其实瓶颈在上游**。
- **修法**：`ConfirmedChapterView` 作为唯一产品口径（只含 CONFIRMED + 重算的正文区间 +
  连续 ordinal + 按 anchorByteStart 排序），并用 `CanonicalChapterDisciplineGateTest`
  **静态扫描生产源码**禁止再出现 `revision.chapters`。
- **教训**：**"接口改了"不等于"数据通了"**。候选/正式混在一个集合里，是最容易被误用的设计；
  要么分类型，要么用静态门把它焊死。

### A3. `chapterIndex` 不可信，却被写成数据库主键

- **现象**：目录顺序错乱、主键冲突。
- **根因**：`BookDatabase` 把 `chapter.chapterIndex` 写进 `ordinal`（PRIMARY KEY），
  而实测 `chapterIndex` 出现过 **8 → 0 回退**。
- **修法**：写 canonical `ordinal`（连续、按 anchorByteStart 升序）；`anchor_byte`（= `chapterId`，
  内容派生）作为稳定标识。
- **教训**：**主键必须来自"有不变式保证"的字段**。加了不变式校验（`ConfirmedChapterView.violations()`）
  之后，"8→0 回退"这类问题会当场暴露成 44,756 条违规 → 0 条。

### A4. `chapterId = 0`（全员同一 ID）

- **现象**：所有章节的持久化键相同 ⇒ 剧本互相覆盖。
- **根因**：`GlobalStructureResolver` 里 `chapterId = 0` 是占位。
- **修法**：内容派生 `chapterId = 锚点行 byteStart`（章节集合变化不影响它）。
- **教训**：占位值一旦进入持久化路径，就是数据损坏。

### A5. `LogicalParagraph.chapterId` 恒为 `null`

- **现象**：**"按章导演"产出 0 段**（`state.json` 里 `totalSegments=0`，状态却是 `COMPLETED`）。
- **根因**：段落构建器里 `chapterId = null` 被硬编码在**两处**，而按章过滤依赖它。
- **为什么没发现**：单测全绿 —— 因为没人对"按章过滤后应产出 > 0 段"写断言。
- **修法**：`LogicalParagraphBuilder.build(chapterOfLine)` 注入闭包（O(1) 游标），
  `ParagraphRecoveryPipeline` 缓存映射。
- **教训**：**每个跨层字段都要有一条端到端断言**（"这个改动在产品的哪条路径上可见？"）。
  编译通过 + 单测绿 ≠ 数据通了。本项目这类事故发生了 **4 次**。

## B. 语义与说话人：最难、也最容易被"指标"掩盖

### B1. 候选名字污染（本项目最贵的一个质量坑）

- **现象**：真机 20 段剧本里 **9 段说话人不是人**（`哈哈`×6、`招呼`×3）。
- **根因**：角色发现输出 371 个"名字"，其中约 **80% 是 cue 子句切片**：
  ```
  李寄舟询 / 张三丰知 / 郭襄再度 / 黑心虎质 / 师妃暄便 / 泥菩萨哂 / 雄霸一边
  倘若 / 因为 / 所以 / 同时 / 可以 / 最终 / 陡然 / 招呼 / 抱拳 / 哈哈 / 虽然不知
  ```
  cue 提取只取"cue 动词前最后一个标点块"，剥掉有限词表后缀后只要剩 2–4 个汉字就当人名。
- **为什么没发现**：**我们一直在报协议合规率**（anchor 100%、coverage 100%、ACCEPTED_ALL），
  从来没有测过"说话人对不对"。模型在被污染的候选里作答，答得完全合规，只是人是错的。
- **修法**：`NameLegitimacy` 闸门 —— ① **全文语料证据**（不同右邻字符数 ≥3 且至少一次独立短语出现）；
  ② 封闭类判据（叹词/虚词/动作短语/介词与指示词起首/程度副词与数词起首/部位短语/虚词前缀/
  结尾虚词字，**称谓后缀豁免**）；③ `真名+1~2字残留` 归并。
  结果：371 → 81（手工标注真名 **74/74** 保留，**290/297** 污染拦下）。
- **教训**：**必须有一条"人工标注（MANUAL_GOLD）才能报准确率"的纪律**。
  没有它，指标会一路绿到底，而产品是坏的。

### B2. 污染会**自我固化**

- **现象**：修好抽取后仍有旧缓存把污染当"真名"用。
- **根因**：`DeliveryCueLexicon.classify` 里有一条安全阀 —— "命中 `knownEntities` 者永不被判为 cue"
  （为了不误吃真名）。但它同时把已经进入实体集的污染**永久保护**了。
- **修法**：叹词/拟声升级为**绝对判据**，排在安全阀**之前**；缓存加 `gateVersion`（版本不符强制重算）。
- **教训**：**任何"安全阀"都要问：它会不会把错误一起保护起来？**

### B3. 语料统计**分不开**高频副词与真名

- **现象**：跨书验证时，长篇《北宋穿越指南》原始候选 3,883 → 接受 1,587，抽样仍看到
  `亲自 / 不由 / 不禁 / 只得 / 后方 / 高兴 / 作揖 / 下意识 / 下定决心`。
- **根因**：`亲自` 在本书出现 **984 次**、右邻字符多样、也常以独立短语出现 —— 语料证据**全部满足**。
  阈值再严会连真名 `刘三刀`（rightKinds=18）一起丢掉。
- **修法（诚实结论：本轮不修）**：需要 **entity type 判据**（PERSON vs OBJECT/PLACE）+
  常用副词封闭类词表 + cue 子句**结构判据**。已登记为 Open Issue，并写明"宁可 UNKNOWN，
  也不把候选集重新投毒"。
- **教训**：**统计证据是必要不充分条件**。当"再调阈值"会同时伤害精度和召回时，说明缺的是
  **另一类判据**，不是更好的阈值。

### B4. 真名自举死循环（规则的"视野"盲区）

- **现象**：16 段对白落 UNKNOWN，而说话人其实是 **雷老虎 / 刘三刀**（全书 42 / 22 次）
  —— 这两个名字**从未被任何一轮发现**。
- **根因**：这本书的 cue 写作两种形态，旧实现都看不见：
  ```
  雷老虎也失笑的摇了摇头：                 ← ① 冒号型：没有说/道动词 ⇒ 找不到 cue
  深吸一口气，雷老虎上前一步，拱手抱拳道：  ← ② 名字不在最后一个块（最后块是"拱手抱拳"）
  ```
  ⇒ 规则层给不出候选 ⇒ 模型只能从"提及"里挑 ⇒ **挑成了李寄舟（错误归属）**。
- **修法**：① 冒号型 cue 也当 cue；② 最后块解析不出人名时，**对子句从右向左回扫已知实体**
  （取块内最靠左的 = 主语位置）；③ **子句里的已知实体优先于块派生的未知表面**。
- **遗留**：通道 ②③ 只能找回"实体集里已有"的名字。自举通道（段首主语提议）实测**有效但不精确**：
  接受集 81 → 414（多出的是 `不可能/但他们/九阳神功/华山派/倚天剑`），已**默认关闭并留下实测记录**。
- **教训**：**"从提及里挑"是错误归属的主要来源**。候选必须来自"说话证据"，不是"文本里出现过"。

### B5. 局部 ID 越界持久化（C18）

- **现象**：早期剧本里存着 `speaker: "C0"` —— 而这个 `C0` 只在**那一次模型请求**里有意义。
- **根因**：局部候选地址被写进了长期数据。
- **修法**：`SpeakerRef = Narrator | Unknown | Character(稳定 opaque id)`；`LocalCandidateResolver`
  在请求边界把 `C#` 翻译成稳定 id；翻译不出来就 **fail-closed**（绝不猜历史 `C0` 是谁）。
- **教训**：**"请求内地址"和"持久身份"必须用不同类型表示**，否则总有一天会被写进数据库。

## C. 协议与模型：prompt 表达问题被误判成模型能力问题

### C1. 模型把**展示标签**回填进协议字段

- **现象**：type 字段不匹配，**96% 硬失败**。
- **根因**：prompt 里写 `S0 [narration]`，模型把 `[narration]` 直接填进 `type`。
- **修法**：展示标签改用**中文方括号**（`〔旁白〕`），与输出枚举（`DIALOGUE`/`NARRATION`）
  在字形上完全不同。
- **教训**：**"模型不会做"和"我们没说清楚"要先分清**。本例是后者。

### C2. 把候选摆给旁白 ⇒ "提到谁就选谁"

- **现象**：旁白段落 15/24 硬失败。
- **根因**：旁白根本没有"谁在说话"这个问题，把候选列表摆上去就是在诱导模型选名字。
- **修法**：旁白走 **shortcut**（不调用模型，直接 `NARRATOR`/`NARRATION`）。
- **教训**：**能让规则确定的，不要问模型**。规则先判断，模型只做残差。

### C3. `parity 不是正确性`

- **现象**：桌面端与设备端输出 **100% 一致**，但两边一起错。
- **教训**：parity 只能证明"确定性"，不能证明"对"。进入语义层后**语义质量优先于 parity**。

### C4. probe 0% 其实是模板坏了

- **现象**：0.8B Base 探针 JSON 合法率 0%。
- **根因**：`chat_template.jinja` 是个 stub。
- **修法**：修模板后 probe 变 VALID（但决策仍退化 ⇒ 定位到"需要 LoRA"）。
- **教训**：**0 分先怀疑管线，再怀疑模型**。

## D. 工程质量：工具链自己就是坑

### D1. 加列不让读路径兼容 ⇒ 点啥闪退啥

- **现象**：用户报"点啥闪退啥"。崩溃栈：
  ```
  SQLiteException: no such column: content_start_line
    at BookDatabase.chapters(BookDatabase.kt:85)
    at ChapterListActivity.onCreate(...)
  ```
- **根因**：给 `chapter_index` 加了正文区间列，**读路径直接按新列 SELECT**，
  而用户旧包的 `book.db` 没有这两列。写入路径有 `ensureSchema` + `ALTER TABLE`，读路径没有。
- **为什么没发现**：开发机上 `book.db` 是新生成的；**旧包只存在于用户设备上**。
- **修法**：读路径用 `PRAGMA table_info` **探测实际列**再拼 SQL（`ChapterIndexQuery` 纯函数），
  缺列降级为 -1 → 调用方回退重编译；并补 `ChapterIndexCompatGateTest`（旧/新/半迁移/空列 4 条）。
- **教训**：**schema 演进必须在读路径上做兼容**，而且要抽成**不需要 Android runtime 就能测**的纯函数。
  "用户设备上的旧数据"是一个必须专门测试的维度。

### D2. O(n²) 把设备卡死

- **现象**：角色档案页打开后设备很卡。
- **根因**：抽取时**每个字符位置都遍历全部名字**（80 名 × 20 万字 = 上亿次 `startsWith`），
  且**每个别称都全量扫一遍原文**（80 × 31 × 20 万）。
- **修法**：① 按首字分桶 + 最长匹配单趟扫描；② 别称在同一趟里判定。
- **教训**：**写 O(n×m) 之前先算一下 n×m**。同类事故还有：Gate 首版对 22 万行做线性 `blank()` 扫描超时。

### D3. PowerShell 单引号里 `` `n `` 是**字面量**

- **现象**：把 `\r\n`（反斜杠r反斜杠n 的字面文本）写进了源码（**3 次**）。
- **根因**：单引号字符串里转义不生效，且 `` `n `` 与 `\n` 混淆。
- **教训**：**改源码用编辑工具，不要用 shell 字符串拼接**。多行 `-replace` 还踩过 2 次行尾
  （CRLF vs LF）失配。

### D4. `[sxsy.org]书.txt` 被 PowerShell 当**通配符**

- **现象**：`Select-String` 扫全部书却**静默跳过**带 `[]` 的文件名（`[sxsy.org]` 是字符类）。
- **修法**：用 `-LiteralPath`。
- **教训**：**"扫了但没命中"和"没扫到"必须能区分**。静默跳过是排查最久的一类问题。

### D5. 关键词搜索 = discovery，不是 proof

- **现象**：`grep` 统计 v90.7 得 **57,126 行**；用 `JSON.parse` 实测是 **14,058 行**。
- **教训**：**冻结事实必须靠结构化解析或针对性验证**。扫描还要覆盖单/双引号与供应商特定格式
  —— 首轮安全扫描就漏检了单引号硬编码 key（现已有合成 fixture 回归）。

### D6. 存在性检查用"正在新增的符号"本身

- **现象**：两次因为"检查某符号是否存在，再决定是否加 import"，结果符号就是本次要加的 ⇒
  跳过 import 导致编译失败。
- **教训**：**判断条件不能依赖待添加的产物**。

## E. 真机环境：与"代码正确"无关，但决定能不能验证

| # | 坑 | 现象 | 处置 |
|---|---|---|---|
| E1 | **logcat 加密** | 本机 `ChapterDirector`/`QwenEngine` 的日志是 `(HKS)…(HKE)` 密文，读不到 | 证据改走**文件/`dumpsys`/UI dump/通知** |
| E2 | **cached-app Freezer** | Activity 承载的长任务被冻结两次（进度停住） | 长任务必须由**前台服务**（`dataSync`）承载 |
| E3 | **厂商安装确认** | `INSTALL_FAILED_ABORTED: User rejected permissions` | 屏幕唤醒后重试；必要时人工点确认 |
| E4 | **内存颠簸** | `free` 只剩 186 MB，跑模型时被 LMK/颠簸 | `am kill-all` + force-stop 占内存的 debug app（曾占 **4.2 GB**） |
| E5 | **无线 adb 不稳** | 无线端点拒绝/掉线 | 优先 USB；无线掉线后 `adb connect` 重连 |
| E6 | **`free` 显示无 cache 列** | Android 的 `free` 不列 buff/cache，`used` 含 page cache ⇒ 误判"内存不够" | 结合 `/proc/meminfo` 与进程 RSS 判断 |
| E7 | **Activity 未导出** | `exported=false` 的页面 adb 起不来（SecurityException） | 驱动走 UI（`uiautomator dump` + `input tap`），或临时用已导出的调试页 |

## G. 方法论级的教训（比单个 bug 更重要）

1. **每个跨层字段都要有一条端到端断言**：问"这个改动在产品的哪条路径上可见？"
   （本项目因缺这条出过 **4 次**事故，其中 1 次让功能完全不可用而单测全绿。）
2. **协议合规率不是质量指标**：没有人工标注就不许报准确率。指标全绿可能只是"问题被定义成了别的东西"。
3. **一次只改一个变量**：本轮修质量时，先修"闸门"，再单独评估"自举通道"；
   因为后者会把接受集从 81 炸到 414，混在一起就分不清是谁的功劳/锅。
4. **失败路线与成功路线同等记录**：本文件就是这条纪律的产物。
5. **宁可 UNKNOWN，不可强造**：UNKNOWN 是可用状态，错误归属是坏数据。
6. **规则的"视野盲区"要靠结构补，不要靠模型补**：模型补的是"残差"，不是"系统性漏检"。
7. **用户设备上的旧数据是一个必须专门测试的维度**（旧 schema / 旧缓存 / 旧剧本）。
8. **文档冲突优先级**：实际代码/测试 > PROJECT_STATE > DECISIONS > 手册 > 旧文档 > 聊天记录。
